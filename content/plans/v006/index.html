04DB Schema 設計

在現有 PostgreSQL 新增 9 張表，分由 profile-service 和 interaction-service 管理。

🔴 CRM 核心表（profile-service 管理）

crm_contacts
├─ id UUID PK
├─ vendor_id UUID? FK -- 關聯建材商
├─ designer_id UUID? FK -- 關聯設計師
├─ name VARCHAR(100)
├─ company VARCHAR(200)
├─ phone VARCHAR(20)
├─ email VARCHAR(200)
├─ grade ENUM(S,A,B,C) -- 客戶等級
├─ source VARCHAR(50) -- 來源管道
├─ assigned_bd_id UUID FK -- 負責 BD
├─ pipeline_stage VARCHAR(30)
├─ total_revenue DECIMAL(12,2)
├─ last_contact_at TIMESTAMPTZ
├─ next_followup_at TIMESTAMPTZ
├─ tags TEXT[]
└─ created_at TIMESTAMPTZ DEFAULT NOW()
crm_activities
├─ id UUID PK
├─ contact_id UUID FK → crm_contacts
├─ bd_user_id UUID FK
├─ type ENUM(call, meeting, email, note, deal)
├─ content TEXT
├─ outcome VARCHAR(100)
├─ duration_min INTEGER
└─ created_at TIMESTAMPTZ DEFAULT NOW()
crm_pipelines
├─ id UUID PK
├─ contact_id UUID FK → crm_contacts
├─ stage ENUM(lead, qualified, proposal, negotiation, closed_won, closed_lost)
├─ deal_value DECIMAL(12,2)
├─ probability INTEGER -- 0-100%
├─ expected_close_date DATE
└─ actual_close_date DATE?
bd_performance
├─ id UUID PK
├─ bd_user_id UUID FK
├─ month DATE -- 月份（每月 1 號）
├─ new_contacts INTEGER
├─ meetings INTEGER
├─ proposals INTEGER
├─ deals_won INTEGER
├─ deals_lost INTEGER
├─ revenue DECIMAL(12,2)
└─ target_revenue DECIMAL(12,2)

🟢 合約表（interaction-service 管理）

contracts
├─ id UUID PK
├─ project_id UUID FK
├─ contact_id UUID FK → crm_contacts
├─ type VARCHAR(50) -- 設計/施工/供貨

├─ location VARCHAR(300)
└─ outlook_event_id VARCHAR(200)? -- Graph API 同步用
daily_reports
├─ id UUID PK
├─ project_id UUID FK
├─ submitted_by UUID FK
├─ date DATE
├─ weather VARCHAR(20)
├─ worker_count INTEGER
├─ description TEXT
├─ materials_used JSONB
├─ issues TEXT
├─ photos TEXT[]
└─ status ENUM(draft, submitted, approved)

📐 Schema 設計原則

  • UUID 主鍵：方便微服務間資料同步、日本站共用
  • TIMESTAMPTZ：所有時間都帶時區，支援台灣 + 日本雙站
  • FK 到既有表：crm_contacts 可選連結 vendor_id 或 designer_id，打通三角色
  • JSONB 彈性欄位：daily_reports.materials_used 用 JSONB，方便擴展
  • outlook_event_id：schedule_events 多一欄紀錄 Graph API 的 event ID，實現雙向同步

09風險 & 對策

自建方案的三大風險及其具體對策。

高風險

風險 1：自建 CRM 功能不夠強

情境：BD 覺得自建 CRM 比不上 Salesforce 的功能豐富度。

對策：
  • 先做核心功能（客戶管理、Pipeline、活動記錄、績效）
  • Week 4 讓 BD 實際使用，收集反饋
  • 每週迭代一次，快速補功能
  • 裝修產業的垂直功能（工程看板、日報、三角色配對）是通用 CRM 根本沒有的——這是差異化優勢
中風險

風險 2：M365 Graph API 限流

情境：200 BD 同時觸發郵件追蹤 / Calendar 同步，Graph API 被限流。

對策：
  • 批次處理（Batch request）：Graph API 支援 $batch，一次送 20 個請求
  • Redis 快取：Calendar 資料快取 5 分鐘，減少 API 呼叫
  • Webhook 優先：用推送而非輪詢，大幅降低 API 呼叫量
  • Graph API 限制：10,000 req / 10 min / app，200 BD 綽綽有餘
低風險

風險 3：開發時間超估

情境：15 天不夠，某些 Sprint 延遲。

對策：
  • 優先順序明確：Sprint A + B（CRM 核心）先上線，Week 2 底 BD 就能用
  • M365 整合（Sprint D）獨立於 CRM 核心，可以延後不影響主功能
  • Frontend 對接（Sprint E）因為已有 UI 原型，只是改資料來源，風險最低
  • 最壞情況：Week 2 底有可用 CRM，Week 6 才完成 M365 整合，仍然可接受

10時程總覽

4 週完成全部開發，Sprint B/C 可並行，最快 Week 2 底 BD 就能開始用 CRM。
